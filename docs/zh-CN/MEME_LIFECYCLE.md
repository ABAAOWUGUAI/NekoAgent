# 表情包生命周期：保存、审核、选择与投递

本文说明产品方向，不把“支持发送图片”误认为“图片语义已经核对”，也不把服务端投递确认误认为客户端显示。公开版与私人实例的实现进度可能不同；以当前仓库代码和实际发行测试为准。

## 参考实现与取舍

- [MaiBot 素材管理](https://github.com/Mai-with-u/MaiBot/blob/main/src/emoji_system/emoji_manager.py)会先按内容哈希保存图片，再建立描述、标签和注册状态；未注册、封禁或文件缺失的素材不进入可用列表。没有配置视觉模型时，它不会把缓存记录当成已完成识别。这个“保存与可发送分离”的方向适合本项目。
- [MaiBot 表情发送工具](https://github.com/Mai-with-u/MaiBot/blob/main/src/maisaka/builtin_tool/send_emoji.py)能让子代理选择候选，但其当前代码在结果无法解析或序号越界时退到候选首张。NekoAgent 不应继承这种失败兜底：未知贴切度应保留已审文字，而不是任取图片。
- [AstrBot 中文发送文档](https://github.com/AstrBotDevs/AstrBot/blob/master/docs/zh/dev/star/guides/send-message.md)和[核心发送工具](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/tools/message_tools.py)提供有序的文字/图片消息组件、图片路径或 URL 处理和发送错误反馈。核心传输能力不等于内建了针对每张表情的视觉语义审核；表情素材管理应在上层应用或插件中完成。

## NekoAgent 应保持的单一链路

1. **保存**：先验证图片格式、大小与文件哈希；相同字节复用同一素材身份。文件已保存只表示“可供审核”，不自动启用。
2. **审核**：审核者基于实际图片记录可见文字、动作和适用语境，同时注明不能从图片推出的事实。来源页标题只作来源信息，不冒充视觉描述；审核方法与所审文件哈希一起追踪。待审、拒绝或缺文件的素材不得进入自动选择。
3. **管理**：现有素材库是唯一资产来源；启用/停用、描述修正和重复文件处理在同一管理入口完成。不建立第二套表情包数据库或暗中重新启用已停用素材。
4. **选择**：先有合格的对话回复，再考虑图片形式。只有图片语义与最终回复及当下话题有具体联系，才把少量已审核候选交给形式选择模型。模型可选纯文字；模型失败、无候选、无效 ID 或不确定贴切度时保留文字，不随机取首张。不靠提高发图频率制造“自然”。
5. **投递**：文本、纯图和图文复用现有 Delivery Outbox。生成、预订、入队、平台 ACK、客户端显示分别记账；一次回复只形成一项逻辑投递。图片组件失败必须暴露失败，不能静默发出空消息。

## 待验证的产品场景

- 有图但与当前回复无关时，最终只发已审文字，且不额外等待选图模型。
- 图内可见文字与描述一致、语境贴切时，图文或纯图能够从唯一 Outbox 到平台 ACK；单次成功不代表目录整体准确。
- 新上传或发现的素材未经实际视觉审核时保持待审；管理页面准确显示状态，并可审核、停用和修正。公开版若尚无完整审核交互，不得把草案写成已上线。

自然体验验收还需足够的新回复样本，分别评估对象、话题、事实、语气、自然度、时机、参与机会与客户端显示；测试通过和 ACK 不能替代这些观察。
